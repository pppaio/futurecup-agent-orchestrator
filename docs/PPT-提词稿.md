## P3 痛点：三个断点

- 编排能力薄弱：脚本化流水线，无条件分支、无异常回退
- 调度策略单一：串行或广播，无能力画像匹配
- **验证与可信机制缺失**：中间结果无自动核对，"幻觉"沿协作链放大

**一句话收口**：前两个已有工程共识，第三个至今没有通用解。

> 口播：验证难，根源不是模型不够强，而是大多数 Agent 的产物"没法被机器判定对错"。

---

## P4 我们的切入点（全场最重要的一页）

**把任务域收窄到"产物可被机器验收"的场景**

一句话需求 → 单文件 HTML 小游戏 → 无头浏览器真跑一遍 → 报错即失败

三个后果：
1. 判定是**二值事实**，不是主观评价
2. 报错可**无歧义回灌**
3. 同一输入可**完全复现**

> 口播：我们主动放弃了"什么都能生成"的野心，换来一件事——**能不能跑，机器说了算。**

## P5 系统架构

（放架构图）

- 前端三页：任务台 / 运行看板 / 核验报告
- 编排引擎：解析器 → 调度器 → 执行器 → 验证门控 → Self-Loop → 人工介入

**收益**：一个设计同时满足 日志 / 快照 / 实时监控 / 轨迹统计 / 断点续跑

## P6 六角色（其中一个是脚本）

| 角色 | 类型 | 职责 |
|---|---|---|
| 分析师 | LLM | 需求 → 可机械验收的规格 |

| 修改者 | LLM | 人工返工时增量修改 |

## P8 智能调度

```
score = 0.4·能力匹配 + 0.3·历史成功率 − 0.2·平均耗时 − 0.1·成本
```

- 就绪队列 + 并发上限 + 能力标签匹配
- 统计量来自历史运行，随使用自我修正

**红线**：跳转只由状态机决定，**禁止 LLM 决定"下一步谁执行"**

---

## P9 自我循环与两级判定（核心）

（放循环图）

```
生成 → 硬验证 → 通过则出关
     → 失败：N 条报错 压成 ≤3 张错误卡片（确定性代码，不用 LLM）
     → 回灌修复者（只喂卡片 + 规格摘要）
     → 轮次 +1
```

- **Fast Path**：能写成 `if` 的判断，绝不交给模型
- **Slow Path**：LLM 只评价"好不好"，且不阻断

---

## P10 凭什么保证循环一定停

四道闸门：
1. 轮次上限 3
2. 调用指纹去重（同一节点同一载荷重复 → 判卡住）
3. 错误数连续两轮不降 → 升级 / 转人工
4. 超限 → **带缺陷交付**（最佳版本 + 缺陷报告），绝不假装成功

**外部观察者**：Loop Watchdog 只读事件流，只看硬信号，**看的不是"进程活着"，是"有没有实质进展"**

---

## P11 中断 / 插入 / 续跑（差异化）

- LLM 与沙箱调用全部异步两段式：`start` → 后台执行 → `finish` 事件回流
- 中断**即时生效**，不等当前调用返回；在途结果标 `orphan` 丢弃
- 全双工：暂停期间仍可输入，续跑时按序注入
- 断点续跑**不重做**已完成节点

> 口播：现在业界公认"用户中途接管 Agent"还没解决好，我们在这一小块给了能跑的答案。

## P12 实验结果

同一批 20 条需求、同一硬验证口径、同一模型：

| 策略 | 可运行率 |
|---|---|
| S1 串行单 Agent | 85% |
| S2 多 Agent 无核验 | 90% |
| **S3 本方案** | **100%** |

**结论**：软裁判只 +5 点，硬验证 + 修复闭环 +15 点。
**增益来自"验证与执行的对抗"，不是 Agent 数量。**

首轮可运行率 95%，唯一失败样本 1 轮修复收敛（曲线 `[1,0]`）；p50 203 s / p95 404 s。

## P14 局限与后续

**主动披露（评委加分项）**
- 硬验证只证明"能跑"，不证明"好玩"
- 样本 20 条，差值不足以做显著性判断
