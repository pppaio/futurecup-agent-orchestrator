## 1 项目概述

### 1.1 项目背景

大模型应用正从"单轮对话"快速演进为"多智能体协作完成复杂任务"。但产业落地中普遍存在三个断点：

**其一，编排能力薄弱。** 现有方案多为脚本化、硬编码的 Agent 流水线，缺乏条件分支、循环控制与异常回退，无法应对复杂任务中的不确定性。

**其二，调度策略单一。** 多数开源框架采用简单串行或广播式通信，缺乏基于任务特征、Agent 能力画像与资源负载的动态分配。

**其三，验证与可信机制缺失。** 这是最致命的一点。Agent 的中间结果与最终结果缺乏自动化验证与交叉核对，多 Agent 协作中的"幻觉"与错误传播难以收敛，系统可解释性与可复现性不足。

前两个断点的解决方案，业界已沉淀出较成熟的工程共识；**第三个断点至今没有通用解**——因为"验证"依赖一个前提：**产物必须可被机器判定**。绝大多数 Agent 应用产出的是文本、方案或建议，对错本身无法机械检验，验证只能退化为"另一个大模型看一眼"，而这恰恰把幻觉从执行层搬到了验证层。

本项目从一个很小的切口进入这个问题：**把任务域收窄到"产物可被机器验收"的软件生成场景，从而使验证成为硬事实而非软判断。**

### 1.2 应用范围

**主场景**：输入一句话需求（如"做一个能玩的打砖块"），平台经多智能体协作生成**单文件 HTML/JS 小游戏或交互小工具**，通过无头浏览器硬核验后交付可运行产物，并附带核验报告。

**为什么限定"单文件、无后端、无依赖"**：这是本项目最重要的一条设计约束，不是能力妥协，而是**验证可靠性的前提**。运行环境完全确定，因此：
- 产物能否运行是**二值事实**，100% 可捕获（加载成功、`console.error`、`pageerror`、画布非空、交互脚本不抛错）；
- 错误信息可**无歧义地回灌**给修复者；
- 同一输入可**完全复现**同一判定。

若允许任意产物形态（多文件、依赖安装、后端服务），验证将退化为不可控的环境调试，闭环立刻断裂。

**可扩展范围**：由于引擎是配置驱动的（角色与工作流均为 JSON 配置，换配置不改代码），同一平台可直接复用于其他"产物可验证"的场景。项目已验证的旁证场景是**文献引用核验**：将"生成者 + 硬校验器"替换为"撰写者 + 引用核验器"（校验 DOI/URL 是否可解析、命中文本是否支持论断），引擎与前端零改动即可运行。

**明确不覆盖**：需要人工审美判断的创意产出、需要真实用户数据的业务系统、跨会话持久在线的个人助理场景——这些场景的验证无法机械化，不在本项目射程内。

### 1.3 核心优势

**优势一：验收由机器判定，不由模型自述。**
平台内置 Playwright 无头浏览器沙箱作为**硬验证**层，判定规则写死：`加载成功 && 零 console 报错 && 画布非空 && 交互脚本不抛错`。这是二值事实，Agent 无法通过"解释"获得通过。LLM 只被允许评价它无法被机械验证的部分（是否好玩、完成度），且其结论**不阻断交付**。这一分工是本项目与同类作品的本质差别。

**优势二：自我循环有外部观察者，而非自我催眠。**
循环内部的自评容易被自身状态污染（修复者永远认为自己在进步）。平台在循环之外配置独立的 **Loop Watchdog**：只读事件流、只看硬信号，监控"有无实质进展"而非"进程是否存活"。判据包括调用指纹去重、错误数连续两轮不降即升级、同错误卡片重复出现即升级。

**优势三：多层循环 + 退步保护 + 版本追溯，不是"修一轮就交差"。**
平台落地了三层收敛循环：**硬修复循环**（≤3 轮，失败即回灌错误卡片）、**评分返工循环**（未达目标分 → 先把当前版本打包留痕 → 问题抛回分析师重读代码重新分析 → 生成者增量改版 → 再评分，轮次上限可配置，默认 3 轮、可开到 9 轮）、**人工返工循环**（人工确认点拒绝 → 带指令回分析师，≤5 轮）。另有两道防退步机制：**门控退步自动回滚**（新版比历史最优差 → 自动回到最优版本再改）与**人工回滚指令**（用户说"返回第一版"，引擎直接从版本文件恢复该版）。每一次评分未满的尝试都会落盘为独立的 `bundle-vN` 版本文件，附对应评分与差距，全程可追溯。

**优势四：智能调度与多供应商，把钱花在刀刃上。**
同类任务可注册多个候选 Agent（如 `builder` 与 `builder-flash`），调度器按 `w_succ·成功率 + w_speed·速度 + w_cost·便宜度` 打分择一，权重可切换「质量优先 / 省流」两档；每个角色的模型、供应商（DeepSeek / 通义千问 / 智谱等 OpenAI 兼容服务）、思考强度均可独立配置，供应商可在界面直接接入（Key 仅存本地）。每一次模型调用的供应商与模型名都写入事件流，可审计。

**优势五：全过程可观测、可干预、可复现。**
所有状态由一条 append-only 事件流派生（18 类事件）。用户可在运行中任意时刻**秒级中断**（直接中止在途模型调用与浏览器验证，实测 1ms 生效）→ 插入新指令或修改需求 → 断点续跑；交付前有**人工确认点**（接受 / 带指令返工）；历史记录页可回看、删除任意一次运行。已完成的节点不重跑，被中止的节点重新入队——这是业界公认尚未解决的"人类中途介入"问题在本场景下的一个可运行答案。

**优势六：失败可解释，不假装成功。**
循环超限时平台执行**带缺陷交付**：输出历史最优可运行版本 + 完整缺陷报告（错误分类、行号、截图、已尝试修法、各版本评分），而不是无限重试或静默失败。

**优势七：工程完整度。**
约 5,900 行 TypeScript（后端 3,534 / 前端 2,361），43 个源文件，20 个可运行命令，303 次真实运行累计、109 个版本文件落盘，54 次提交全链可追溯，多份规格与文档。全部命令**在无 API Key 时可用 Fake LLM 零成本复现**。

## 2 解决方案

### 2.1 总体架构

```
┌────────── 前端四页（React + Vite）──────────┐
│ ① 任务台   ② 运行看板   ③ 核验报告   ④ 历史记录 │
└───────────────────┬────────────────────────┘
              REST + SSE（事件直推，前端不轮询）
┌───────────────────┴────────────────────────┐
│ 编排引擎 Core（纯逻辑，无 IO 副作用，可单测）│
│ 解析器 → 智能调度器 → 执行器 → 硬验证/质量门控│
│ → 三层循环控制器 → 人工介入控制器            │
│ + Loop Watchdog（外部只读观察者）            │
└───────────────────┬────────────────────────┘
┌───────────────────┴────────────────────────┐
│ 可插拔能力层                                 │
│ 多供应商 LLM Gateway / 沙箱 / 工具层 / 打包器 │
└───────────────────┬────────────────────────┘
        events.jsonl（唯一事实来源）+ runs/artifacts
```

**核心架构决定：事件溯源（Event Sourcing）。** 系统不维护"当前状态表"，所有状态均由 append-only 事件流派生投影。事件类型共 18 类：`run.started/finished/failed`、`node.entered/exited`、`agent.thinking.delta`、`agent.message`（含每次调用的供应商/模型留痕）、`agent.tool.call/result`、`artifact.created`、`verify.hard.result`、`verify.soft.verdict`、`loop.iteration`、`run.interrupted/resumed`、`human.instruction`、`scheduler.picked`、`error`。

一项设计同时兑现五项能力：

| 赛题要求              | 实现方式                             |
| 执行日志              | 事件流即日志                          |
| 状态快照 / 可复现      | 事件流 + 产物 sha256 可完整重放       |
| 实时监控              | SSE 直推事件，前端不轮询              |
| 轨迹（时长/轮次/调用） | 对事件流做聚合查询                    |
| 中断后续跑            | 断点 = 事件流位置 + 各节点最新输出引用 |

### 2.2 Agent 团队定义

平台定义 5 类角色，其中**1 类不是 LLM**——这是刻意的设计：

| 角色 | 类型 | 职责 | 输入 → 输出 |
|---|---|---|---|
| 分析师 analyst            | LLM | 把一句话需求拆成**可机械验收**的规格；返工轮结合裁判差距+上一版代码+用户指令重新分析，输出修订规格与具体修改要求 | 需求(+返工材料) → DecompositionSpec |
| 生成者 builder            | LLM | 产出单文件 HTML；返工轮基于上一版做**增量修改**（不推倒重做） | 规格(+上一版) → HtmlArtifact |
| **硬校验器 hard-sandbox** | **确定性脚本** | 无头浏览器加载、捕获报错、截图、判定 | 产物 → HardReport |
| 软裁判 critic             | LLM | 对照验收条件打分（1~5）、指出偏差；**对比历史各版判断进步/退步** | 产物+规格+历史 → SoftReport |
| 修复者 fixer             | LLM | 吃错误卡片/改进卡片重写产物 | 卡片+规格+摘要 → 新产物 |

每个角色是一个 `AgentProfile`：角色提示词、版本号、思考强度、模型（供应商可任意）、能力标签、工具白名单、记忆范围、输出 Schema、**调度指标（历史成功率/平均耗时/成本档位）**。

**智能调度候选池**：同一任务可注册多个候选（当前：`builder` 与 `builder-flash`），调度器按打分择一（见 2.4）。

**分析师输出契约（关键设计）**：除 `acceptance[]`（每条必须能被程序判定真假）、`assumptions[]`（替用户做的默认决定）、`ambiguities[]`（不确定点，标 `blocking`）外，还输出 `tasks[].spec`（任务书级实现要点：数据结构、状态变量、更新规则、数值区间、交互映射、边界情况）与 `changes[]`（返工轮的具体修改要求）。当阻塞性歧义数 > 0 时**停机转人工**，而不是猜下去。

> 这一条把"人工介入"从演示技巧变成了架构必需品：**任务本身有歧义时，停在歧义点比猜错三个节点便宜。**

### 2.3 工作流编排

工作流用 JSON 描述为 DAG（含回边成环），节点支持 `agent / verify / packager / human / gate / subflow` 六类，边支持四种控制结构：

| 结构 | 实现 |
|---|---|
| 顺序     | 单边链 |
| 并行分支 | 同源多边 |
| 条件判断 | 边属性 `when: always / pass / fail` |
| 循环迭代 | 回边 + `loop.max_iters` + 超限兜底 `on_exhaust` |
| 子工作流 | 节点类型 `subflow`（自主编排模式使用） |

**循环不做特殊处理**：回边在运行时等价于"该节点重新入队"，靠局部 `loop.max_iters` 与全局 `limits.max_total_iters` 双重兜底。这样既保留 DAG 的静态可校验性，又支持迭代。

**主工作流 `game-gen-v4`（固定流水线模式）**：

```
分析 → 生成 → 硬验证 ──失败──> 修复者 ──循环(≤3轮)──> 硬验证
              └─通过─> 软裁判评分 ──> 质量门控
                          ├─ 达目标分 ──> 交付打包 ──> 人工确认点
                          │                              ├─ 接受 ──> 完成
                          │                              └─ 返工(带指令) ──回分析师──> 生成者增量改──> …
                          └─ 未达目标分 ──> 版本留痕(bundle-vN) ──> 回分析师(读代码+差距+历史教训)
                                └──> 生成者增量改 ──> 再验证再评分 ──> 循环(轮次可配，默认3轮/上限9轮)
```

**自主编排模式 `auto-plan-v2`**：分析师额外输出**开发计划**（2~4 步，每步含验收点），引擎确定性地把计划逐步编排为「生成 → 硬验证 → 失败修复」子流程（`subflow`），上一步产物增量传给下一步；后续评分/返工/人工确认与固定模式共用同一套门控。**LLM 只提供计划数据，步骤编排由引擎代码执行**——控制面确定性红线在动态编排下依然成立。

### 2.4 智能调度引擎

调度器采用「OR 激活 + 就绪队列」模型：任一条入边条件满足即触发目标节点，节点入队按序消费，`max_concurrency` 声明并发上限；一次取出至多上限个就绪节点交给并发 Worker，主循环不等单个节点。

Agent 分配由 `pickAgent(node, candidates[])` 完成，打分函数（各分量归一化到 0~1）：

```
score = w_succ·成功率 + w_speed·速度 + w_cost·便宜度
```

权重随**调度档位**切换：质量优先 `{1.0, 0.05, 0.03}`（选强模型），省流 `{0.3, 0.2, 0.5}`（选便宜模型）。实测同一生成节点在两档下分别选中 `builder`（0.983 vs 0.915）与 `builder-flash`（0.768 vs 0.417），打分过程以 `scheduler.picked` 事件留痕。四个分量均来自角色画像（bench 实测成功率、平均耗时、成本档位），调度随运行积累可自我修正。

**控制面确定性（红线）**：节点跳转只由 WorkflowDef + 状态机决定，**禁止 LLM 决定"下一步谁执行"**。LLM 只产出结构化数据，不得改变拓扑。调度打分、质量门控、退步回滚、版本恢复、错误归一化**全部是确定性代码**。

> 这条红线的现实依据：业界实测表明，若把"是否分派、分派给谁"交给模型临场判断，会出现不可控的长尾（同一提示词下模型时而分派时而不分派），且不可复现。**能写成 `if` 的判断，绝不交给模型。**

### 2.5 自我循环与验证（核心）

**两级判定（Fast Path / Slow Path）**：

| 层级 | 判定者 | 判定对象 | 是否阻断 |
|---|---|---|---|
| L1 硬验证 | 沙箱脚本（**非 LLM**） | 能否加载、有无报错、交互是否抛错、画布是否非空 | **是**，失败即回灌 |
| L2 软验证 | LLM 裁判 | 是否满足验收条件、完成度 1~5 分、相对历史的进步/退步 | 否，作为质量门控输入 |
| L3 人工   | 用户 | 最终验收 / 中途干预 / 返工指令 | 是 |

**三层循环**：

1. **硬修复循环（≤3 轮）**：硬验证失败 → 错误归一化（N 条报错 → ≤3 张错误卡片，分类为语法/运行时/渲染/交互，附行号与截图）→ 回灌修复者（只喂错误卡片 + 规格摘要，不喂全文，控 token）→ 轮次 +1。归约器是确定性代码，禁用 LLM。
2. **评分返工循环（轮次可配，默认 3、上限 9）**：软裁判打分未达目标分（默认 5，可调 3/4/5）→ **先把当前版本打包留痕（`bundle-vN`，每个未满分的尝试都可追溯）** → 差距压成改进卡片 → **回分析师**（输入：原始需求 + 裁判差距 + 上一版完整代码 + 历史教训 `run_memory`）→ 分析师输出修订规格 + `changes` 具体修改要求 → **生成者基于上一版增量修改** → 再验证再评分。
3. **人工返工循环（≤5 轮）**：人工确认点拒绝并附指令 → 回分析师（结合指令+当前版本重新分析）→ 生成者增量改 → 再走完整验证闭环。

**两条防退步机制**（针对"越改越差"）：

- **门控退步自动回滚**：门控持续记录历史最优版本；新版评分低于最优 → 自动把工作基底回滚到最优版本并附说明卡片，后续修改基于最优版而非坏版本；
- **裁判对比历史**：裁判输入含历史各版本得分，规则要求明确指出相对退步点并相应降分；
- **人工回滚指令**：用户说"返回第一版 / 回到第 N 版" → 引擎直接从 `bundle-vN.html` 恢复该版本作为后续修改基底。

**四道收敛闸门**（Loop Watchdog，外部只读观察者）：

1. **轮次上限**（各循环局部上限 + 全局 `max_total_iters`）；
2. **调用指纹去重**：`hash(节点 + 规范化载荷)` 重复，或错误卡片集合与上轮相同 → 判"卡住"，立即升级；
3. **错误数连续两轮不降** → 升级策略（拆更细子任务 / 提高思考强度 / 请求人工）；
4. **超限带缺陷交付**：输出历史最优可运行版本 + 缺陷报告，绝不假装成功。

**质量门控也是确定性代码**：分数与阈值比较、版本留痕、退步回滚、卡片压缩——没有任何一步是 LLM 决策。

### 2.6 人工介入与可复现

**中断 / 插入 / 续跑**是平台的差异化能力：

```
running --interrupt()--> paused --resume(instruction)--> running
```

- **秒级中断**：中断直接 `Abort` 所有在途模型调用与浏览器验证（实测 1ms 生效），被中止的节点**重新入队**，续跑后从头再跑；不再需要"等当前调用返回才暂停"。
- **全双工**：`paused` 期间用户仍可输入，指令进队列，`resume` 时按序注入。
- **续跑不重做**：已完成节点的输出直接复用，仅从断点继续。
- **人工确认点**：交付前暂停等用户拍板——接受交付，或带指令返工（回分析师）。

**历史与可追溯**：每次运行落盘 `events.jsonl`（18 类事件）、`run.json`（模型快照含供应商、错误曲线、耗时）、`hard_report.json`、`bundle-vN` 全部版本、验证截图。历史记录页从磁盘扫描（服务重启不丢），运行中项目置顶并自动刷新，支持一键删除（运行中的先秒级中断再删除）。

**可复现三件套**：`run.json`（模型版本快照、产物 sha256、错误曲线、耗时）+ `events.jsonl`（完整事件流）+ `hard_report.json`（硬验证明细）。`replay` 命令可完整重放任意一次运行。

### 2.7 技术选型与工程实现

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | TypeScript + Node 20 | 与 Playwright 同生态，前后端共享类型 |
| 沙箱 | Playwright（chromium headless） | 可捕获 `console`/`pageerror`，可截图，可脚本化交互 |
| 存储 | JSONL 事件流 + 文件系统 | 追加写最契合事件溯源，无需数据库 |
| 前端 | React + Vite，四页 | 任务台 / 运行看板 / 核验报告 / 历史记录 |
| 模型 | 多供应商网关（OpenAI 兼容） | DeepSeek / 通义千问等可在 `.env` 配置或在界面直接接入，Key 仅存本地 |
| 框架 | **不使用 LangChain / Dify 作为骨架** | 保证调度、验证、自循环三层为自主实现 |

**模块规模**：后端 3,534 行（31 文件）、前端 2,361 行（12 文件），合计约 5,895 行 / 43 文件。

**20 个可运行命令**覆盖：最小闭环（`demo:single`）、全链路（`demo:workflow`）、卡死检测（`demo:stall`）、中断续跑（`demo:interrupt`）、歧义停机（`demo:gate`）、质量返工（`demo:quality`）、人工确认（`demo:confirm`）、调度对比（`demo:scheduler`）、自主编排（`demo:auto`）、退步回滚（`demo:rollback`）、真实模型（`demo:real`）、批量实验（`bench` / `compare` / `summary` / `charts`）、事件重放（`replay`）、服务（`serve`）、导出（`export:doc` / `export:ppt`）、类型检查（`typecheck`）。

**无 Key 可复现**：未配置 API Key 时自动使用 Fake LLM，全部流程零成本可跑通。这是本项目对"可复现性"评分项的直接回应——**评审无需为验证一个学生作品而充值**。

### 2.8 与同类框架的关系

项目对标 LobeHub、DeepSeek Harness 等主流 Agent Harness 框架，但定位不同：

| 维度       | 通用 Harness | 本项目 |
| 目标      | 持久的、跨会话的通用智能体运行时 | 单次任务内**产物可被机器验收**的闭环 |
| 核心难题  | 上下文连续性 / 并发吞吐 / 多信道 | **验证的可信度与循环的收敛性** |
| 差异点    | — | 硬验证沙箱、三层循环、退步回滚、带缺陷交付、版本追溯 |

**本项目未基于任何现有框架二次开发**，调度器、验证门控、循环控制器、Watchdog、事件溯源引擎均为自主实现。我们在设计过程中独立收敛到了与业界相同的一条结论——**控制面必须确定性、上下文必须切片隔离**——这恰好验证了该结论的正确性，而非相反。

## 3 应用成效

### 3.1 验证方法

**数据集**：20 条需求，5 类 × 4 条，覆盖不同复杂度——经典玩法复刻（打砖块/贪吃蛇/俄罗斯方块/扫雷）、机制微创新（带重力的俄罗斯方块等）、交互小工具（番茄钟/计算器/倒计时/单位换算）、多维需求（记忆翻牌含计分计时难度切换等）、边界歧义需求（"做个好玩的游戏"）。

**对照设计**（同一批样本、同一硬验证口径、同一模型）：

| 策略 | 说明 |
|---|---|
| S1 串行单 Agent（基线） | 分析 → 生成，无核验、无修复 |
| S2 多 Agent 无核验 | 分析与生成分离，加软裁判，但无硬验证门控 |
| S3 本方案 | DAG + 硬验证门控 + 修复循环 + Watchdog |

S2 的存在是为了回答一个必被追问的问题：**增益来自"Agent 数量"还是"验证闭环"？**

**指标口径**：以 L1 硬验证（`load_ok && errors==0 && canvas_nonempty && 交互无异常`）为唯一判定，机器计算、不可争辩。

### 3.2 实验结果

| 策略 | 可运行数 | 可运行率 |
|---|---|---|
| S1 串行单 Agent    | 17/20 | 85% |
| S2 多 Agent 无核验 | 18/20 | 90% |
| **S3 本方案**      | **20/20** | **100%** |

**结论一：软裁判只带来 5 个百分点（85%→90%），硬验证 + 修复闭环带来 15 个百分点（85%→100%）。增益来源是"验证角色与执行角色的对抗"，而非 Agent 数量。**

**结论二**：本方案 20 条样本**首轮可运行率 95%（19/20）**，唯一首轮失败的是 d3「贪吃蛇+排行榜」（首轮 1 条报错），经 1 轮修复收敛，错误曲线 `[1, 0]`。

**性能**：p50 = 203 s，p95 = 404 s（长尾来自机制微创新类样本的深度推理）。

**成本**：三策略对比共 161 次模型调用，输入 166,069 token + 输出 646,302 token（含思考 507,451），合计约 **¥9.47**（闲时计价）；20 样本基准另计约 ¥3.71。

**持续实证规模**：平台累计真实运行 **303 次**（批量实验、机制演示、真实模型全流程走查、人工实测），落盘 **109 个版本文件**——"循环、返工、版本追溯"不是文档里的名词，而是 303 次运行中反复执行过的机制。

### 3.3 应用案例

**案例一：d3「贪吃蛇，含排行榜和速度调节」——完整闭环收敛的实证。**
首轮产物在排行榜渲染处抛出 1 条运行时错误，被沙箱捕获并归一化为 1 张错误卡片（分类：运行时，附行号）。修复者仅收到该卡片与规格摘要，第二轮输出消除错误，错误曲线 `[1, 0]`，最终 `ok=true`。**这是"执行→验证→修正"闭环完整跑通并收敛的实证。**

**案例二：e1「做个好玩的游戏」——歧义停机。**
分析师判定为阻塞性歧义（需求无任何具体玩法），输出 `ambiguities[{q:"未指定玩法类型", blocking:true}]`，平台在 `human gate` 暂停并抛给用户，而非自行猜测。用户补充"做成打砖块"后作为 `human.instruction` 注入并续跑，产出正常交付。**对照中 S1 在此类样本上倾向自行假设，产物与用户预期存在偏差风险。**

**案例三：评分返工循环收敛（机制验证）。**
质量门控实测：软裁判首版打 2 分（未达目标）→ 版本留痕 → 差距回分析师 → 生成者改进 → 再评分 5 分 → 交付，打分序列 `[2, 5]`，两版产物均可追溯。真实模型运行中同样反复触发过该循环（裁判低分 → 自动返工 → 收敛至确认点）。

**案例四：退步保护与人工回滚（机制验证）。**
构造"首版 4 分 → 返工后 2 分（退步）"场景：门控自动回滚到最优版本并附「本版退步，已自动回退」卡片；随后人工指令「返回第一版」被引擎识别，从 `bundle-v1` 恢复该版本作为修改基底，全程 4 个版本文件可查，最终正常交付。**"越改越差"与"改不回去"两个常见痛点均有机制兜底。**

**案例五：自主编排 + 多供应商混跑（真实模型）。**
一句"做个能玩的贪吃蛇"，分析师（通义千问 qwen-max）拆出多步开发计划，引擎逐步编排"生成→验证→修复"（单次运行 28 个步骤事件），生成者（DeepSeek v4-pro）逐步实现，软裁判（DeepSeek flash）评分并触发返工，全部调用的供应商与模型以 `meta` 事件留痕可审计——**跨供应商协作、动态编排、质量门控在同一次运行中同时发生。**

### 3.4 局限与诚实披露

1. **L1 只证明"能跑"，不证明"好玩"。** 对图形类需求依赖 `canvas_nonempty` 这类弱信号，无法判定玩法是否符合预期，后者交由软裁判与人评。
2. **简单域循环触发率低。** 在"经典玩法复刻"这类任务域，19/20 首轮通过，硬修复循环仅被触发 1 次；评分返工循环因目标分默认 5 分触发更频繁，但尚未做大规模统计。高难度样本补充实验（弹幕射击/平台跳跃两条）已备好数据集与跑批命令，受预算限制未跑完，结论留白。
3. **单模型单次采样。** 未做多 seed 重复实验，未做方差分析。
4. **结构性延迟。** 每个节点都是一次模型往返，简单任务上多 Agent 耗时高于单 Agent。本项目**不以"更快"为卖点，而是以"一次通过率与可信交付"为卖点**。
5. **单点脆弱性。** 分析师的拆解错误会向后传导。缓解手段是歧义停机、退步回滚、优化提示词与裁判对比历史，但无法根除。
6. **维护成本。** N 个角色 = N 套提示词 + N 套 IO Schema，改一个角色的输出格式需同步改下游。
7. **循环上限与成本的权衡。** 评分返工轮次开满（9 轮 × 全强模型）会显著放大 token 成本，默认档（3 轮、目标 5 分）是质量与成本折中；平台把轮次/目标分做成运行级可配置，让用户在钱与执着之间自行权衡。

## 4 商业模式

> 本章面向学生创新项目的落地路径，不做营收预测，只说明价值链条与可行性。

### 4.1 推广模式

**路径一：高校课程与实训（主路径）。**
"AI 原生应用开发"已成为计算机、软件工程专业的必修或选修方向，但教学普遍停留在"调 API"层面，缺乏"如何让模型产出可靠交付物"的工程训练。本项目可直接作为课程实验平台：教师配置工作流与验收条件，学生观察多 Agent 协作与验证闭环，把抽象的"Agent 工程"变成可运行、可打分的实验。落地成本极低——单机、无 Key 可跑。

**路径二：竞赛培训与赛前集训。**
同类赛事（含本赛事的后续届次）的参赛队伍普遍需要"可运行、可演示、可复现"的工程基线。本项目可作为赛前集训的开源底座。

**路径三：开源社区扩散。**
仓库以宽松协议开放，提供场景模板市场（工作流 JSON + 角色组配置），鼓励社区贡献"新场景模板"而非改动引擎，形成低门槛贡献路径。

### 4.2 市场空间

**直接需求侧**：教育机构（课程实验平台）、企业研发团队（内部工具生成的效率工具）、外包与交付型团队（原型快速成型）。

**需求真实性的判断依据**：当前"AI 生成代码"的瓶颈已从"能不能写"转移到"写完能不能信"。企业引入 AI 编码工具后最普遍的成本不是 token，而是**人工复核**。任何能把复核环节自动化一部分的方案，都有明确的降本空间。本项目在"产物可机械验收"的窄域内做到了这一点。

**规模判断**：本项目不追求通用编程市场，聚焦"可验收的小型前端产物"这一细分域——包括教学实验、原型验证、内部小工具、轻量游戏与可视化 demo。该细分域的特点是**产物小、验收标准清晰、失败代价低**，恰好是自动化闭环最易成立的区间。

### 4.3 生态运作

**开源内核 + 场景模板 + 服务** 三层结构：

| 层 | 内容 | 策略 |
|---|---|---|
| 内核 | 编排引擎、沙箱验证、Watchdog、事件溯源、多供应商网关 | 开源免费，接受社区贡献 |
| 模板 | 游戏生成、引用核验、数据看板、可视化 demo 等工作流配置 | 社区共建，官方维护标杆模板 |
| 服务 | 私有化部署、自定义验收规则、行业场景适配 | 面向院校与企业收费 |

**与主办方生态的协同**：本项目的硬验证范式（"任何产物都要有一个机器可判的验收口径"）可迁移至同赛事的其他赛道——例如 AI4S 场景中的"计算结果可复现性校验"、OpenHarmony 场景中的"原生应用编译与安装校验"。这套"验证优先"的工程方法论，比具体代码更具生态价值。

**可持续性**：项目不依赖专有模型或专有数据，所有组件均为开源可替代；维护成本集中在模板与验收规则，而非内核，适合小团队长期运营。

## 附录 A 人工智能使用说明（各环节 LLM 的实际作用与边界）

| 环节 | 使用了什么 | 实际作用 | **边界（哪些判断没交给它）** |
|---|---|---|---|
| 需求拆解 | LLM（分析师） | 把自然语言需求转为可机械验收的条件 | 是否停机追问由**规则**判定（阻塞性歧义计数 > 0） |
| 产物生成 | LLM（生成者） | 产出/增量修改单文件 HTML | 生成什么结构由规格约束，不得自选技术栈 |
| 运行验证 | **不使用 LLM** | — | 判定"能不能跑"完全由沙箱脚本完成 |
| 质量评价 | LLM（软裁判） | 对照验收条件打分、对比历史指出退步 | **不阻断交付**；是否返工由质量门控规则判定 |
| 错误修复 | LLM（修复者） | 依据错误卡片重写 | 修几轮由**轮次上限**与**指纹去重**控制，不由模型决定停止时机 |
| 错误归一化 | **不使用 LLM** | — | 确定性代码压缩错误卡片 |
| 任务分派 / 调度打分 | **不使用 LLM** | — | 由 WorkflowDef + 状态机 + 打分函数决定，禁止模型改拓扑 |
| 质量门控 / 退步回滚 / 版本恢复 | **不使用 LLM** | — | 分数阈值比较与版本切换都是确定性代码 |
| 进展判断 | **不使用 LLM** | — | Watchdog 只读硬信号（错误数、指纹、超时） |
| 自主编排（计划执行） | LLM 只出计划数据 | 分析师拆步骤 | 步骤如何编排执行由引擎代码决定 |

**一句话概括**：LLM 负责"生成"与"评价好不好"，**不负责"判定能不能跑"，也不负责"决定何时停、改哪个版本、分派给谁"**。这三条边界，是本项目对"AI 使用合理性"的直接回答。
