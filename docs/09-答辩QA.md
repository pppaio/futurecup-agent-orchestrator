# 答辩 Q&A 速查（含实验数据版）

> 按 docs/03 的 6 问扩写，加上实验数据可能引发的追问。答辩前背这一份就够。

---

**Q1：你们和 Dify / LangChain 有什么区别？**

它们是编排框架，我们是**带闭环验收的编排平台**。三点本质区别：① 我们的产物流入无头浏览器实测，能不能跑是二值事实，不是模型自述；② 调度跳转由 WorkflowDef + 状态机决定，禁止 LLM 临场决定"下一步谁执行"（业界实测交给模型会产生长尾）；③ 循环有外部观察者（Loop Watchdog）用硬信号把关，不是"再试一次"。

**Q2：多 Agent 有必要吗？一个 Agent 多调几次不行吗？**

我们的三策略对比（S1 串行单 Agent 85% / S2 多 Agent 无核验 90% / S3 本方案 100%，同一 20 样本、同一硬验证口径）就是用来回答这个的：**多 Agent 本身不值钱，值钱的是验证角色和执行角色的对抗关系**。软裁判只提 5 个点（85→90），硬验证 + 修复闭环提 15 个点（85→100）。硬验证沙箱不是 Agent，它不给生成者面子；软裁判和生成者是两套 Prompt、两套判定，交叉降低自说自话的概率。

**Q3：LLM 裁判会不会被幻觉骗？**

会，所以我们**不让它判定"能不能跑"**。能不能跑是沙箱判的（加载、报错、渲染、交互），是二值事实。LLM 裁判只被允许评价机器测不了的部分（好不好玩、完成度），而且它的结论不阻断交付——软评分低只作为提示与人工介入的触发信号。这在文档里叫两级判定 Fast/Slow Path。

**Q4：怎么保证循环一定停？（重点必考）**

四道闸，全部落码且由**外部只读观察者**判定：① 轮次上限 3；② 错误数连续两轮不降 → 升级；③ 错误卡片集合重复 → 升级（没抓到根因）；④ 修复者输出与上轮完全相同 → 中止（防御性妥协当场抓包）。超限则**带缺陷交付**：输出最佳版本 + 缺陷报告，绝不假装成功。本质区别：循环有外部观察者，且观察者看硬信号不看 Agent 自述。

**Q5：你们这个算什么创新？**

不在算法复杂度，在**闭环的设计**：把"产物可机器验收"这个前提用足了——所以验证是硬的、可复现的、不可争辩的；再用事件溯源把过程和产物绑定——所以可审计、可回放、可中断续跑（快照=事件流末尾位置，不另建状态表）。行业里"用户中途接管 Agent"还是公认的开放问题，我们给出了能跑的实现（中断→插入指令→断点续跑 + 歧义自动停机）。

**Q6：exe 能生成吗？**

架构里留了可插拔打包器接口（SingleHtmlPackager 是当前实现，Tauri/Electron 是 roadmap 空实现）。我们刻意不把 11 天工期赌在打包调试上，路是通的。

**追问 1：为什么修复轮次那么少（中位数 0）？是不是修复循环没被验证？**

两个层面答：① 真实模型 v4-pro 本身很强，20 样本里 19 个首轮通过，说明 Builder Prompt 与验收口径设计有效；② 修复闭环被**两处独立证据**验证过：真实样本 d3（贪吃蛇+排行榜）首轮 1 条报错经 1 轮修复收敛 `[1,0]`；另有 demo 级验证——`demo:workflow`（故意注入坏代码 → 修复 → 通过）和 `demo:stall`（修复者反复交坏代码 → 看门狗升级中止）。机制正确性用受控实验证明，统计数字用真实样本给出。

**追问 2：p95 耗时 404s 为什么是 p50（203s）的两倍？**

机制微创新类样本（如"俄罗斯方块但每个方块有不同重力"）需要模型深度推理游戏规则与数据结构，单样本 4~6.7 分钟。这正是多 Agent/编排系统的真实长尾——所以我们坚持报 p95 不报均值，长尾才是系统的真实成本。

**追问 3：成本怎么算的？**

实验用 DeepSeek 官方峰谷计价（闲时半价），全实验 61 次 LLM 调用、输入 73,207 + 输出 250,056（含思考 202,018）token，约 ¥3.71。省成本靠三件事：上下文切片（每个节点只收到声明需要的 port）、阅后即焚（思考流不进下一节点）、确定性归约（能写成 if 的判断不烧 token）。

**追问 4：实验里第一轮全部误杀工具类，是不是说明系统不成熟？**

正好相反，这是真实实验的价值：第一轮 bench 暴露了沙箱对 DOM 工具的判定缺陷（无条件要求 canvas），我们定位根因 → 修复（graphic 类型条件判定 + 信号失败进错误卡片）→ 第二轮全量复测 20/20。**"发现问题→定位→修复→复测"的闭环就是我们平台方法论的实践**，方案书里完整记录了这个迭代。

**追问 5：歧义需求（"做个好玩的游戏"）你们怎么处理？**

分析师把需求拆成 acceptance + assumptions + ambiguities，`blocking:true` 的歧义会触发**歧义停机**——暂停、把问题抛给用户、回答后续跑（demo:gate 实测）。这让人工介入从"演示技巧"变成"架构必需品"：任务本身有歧义时，停在歧义点比猜下去便宜。批量实验中该开关可关（humanGate 选项），保证实验吞吐。

**追问 6：工具类产品没有 canvas，你们的"可运行"判定会不会太弱？**

工具类判定 = 加载成功 + 零报错 + DOM 节点数 ≥ 12（有实际界面内容）+ 交互不抛错。我们承认 DOM 节点数是弱信号，已在方案书"诚实局限"里写明；更细的验收（按钮是否可点、计时是否走动）依赖交互脚本（验收条件 → 小型交互 DSL → Playwright 脚本），这是 roadmap。

**追问 7：只测了 20 条样本，结论可信吗？**

不可外推，我们自己也这么写。20 条 = 5 类 × 4 条，覆盖的是"小游戏/小工具"这个选定产物的代表性分布；结论边界明确（方案书 §8.3）。若要更强的统计力，加多 seed 重复与更大样本即可——流水线（bench/compare 命令）已支持。
