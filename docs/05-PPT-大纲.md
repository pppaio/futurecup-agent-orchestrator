## P2 痛点
- AI 生成的代码"看着对、一跑就崩"，还得人工核验
- 多 Agent 协作的幻觉会向下游传播，没人把关
- 一句话主张预告

## P3 核心主张
- **「能不能跑，机器说了算。」** LLM 只负责生成和评价，不负责判定能否运行
- 验收是二值事实：加载、报错、渲染、交互

## P4 系统总览（一句话 → 可运行产物）
- 输入"做个能玩的打砖块" → 分析 → 生成 → 硬验证 → 修复 → 打包 → 交付
- 一张主流程图（背下来画白板就是这个）

## P5 总体架构
- 三层 + 一份存储：前端(三页) / 编排引擎 Core / 可插拔能力层 / 事件流
- 关键决定：**事件溯源**（一份设计同时满足日志/快照/监控/轨迹/复现）

## P6 五个核心模块（对齐评分表）
| 模块 | 一句话 |
|---|---|
| Agent 定义 | 谁干、能干什么 |
| 工作流编排 | 活按什么顺序干 |
| 调度执行 | 谁先干、同时干几个 |
| 结果验证 | 干得对不对 |
| 反馈优化 | 不对就改，改到对 |

## P7 五角色 + 工作流 DAG
- 分析师 / 生成者 / 硬验证沙箱 / 软裁判 / 修复者
- DAG 支持：顺序 / 并行 / 条件 / 循环

## P8 硬验证沙箱
- Playwright 无头浏览器：加载 + console/pageerror 全捕获 + canvas 非空 + 交互
- 判定规则写死，不可争辩、可复现

## P9 Self-Loop + Loop Watchdog（灵魂）
- 失败 → 错误卡片(≤3张) → 回灌修复 → 再验证，≤3 轮
- 四道闸：轮次上限 / 错误数连续两轮不降即升级 / 错误卡片重复即升级 / 输出指纹去重即中止
- **循环有外部观察者，看硬信号不看 Agent 自述**

## P10 两级判定 Fast / Slow Path
- 硬验证（确定性代码）判定"能不能跑"；软裁判（LLM）只评价"好不好"，不阻断
- 能写成 if 的判断，绝不交给模型

## P11 可中断 · 可复现
- 运行中中断 → 插入指令 → 断点续跑（人工介入节点）
- 每次运行落盘 run.json + events.jsonl，可重放
