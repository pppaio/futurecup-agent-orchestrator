## 30 秒电梯演讲

> 现在你让 AI 写个小游戏，它经常给你一段看着对、一跑就崩的代码，你还得人工核验。
> 我们做了一个多智能体编排平台：分析师先把需求拆成可验收的条件，生成者出代码，然后**用无头浏览器真跑一遍**——报错就是报错，Agent 没法自我说服。失败了把错误压成卡片回灌给修复者重写，最多三轮。
> 关键在于：**能不能跑，机器说了算，不交给模型判断。** 在我们 20 条需求的测试里，一次可运行率从 __% 提到了 __%。
> 而且跑的过程中你随时能看到每个 Agent 在干什么，觉得方向不对可以中途掐断、加一句要求、从断点继续。

## 五个模块 = 五句话（正好对上评分表）

| 模块 | 一句话 | 大白话 |
|---|---|---|
| Agent 定义 | 每个角色有角色、模型、能力标签、工具白名单 | 谁来干、能干什么 |
| 工作流编排 | 用 JSON 描述 DAG：顺序/并行/条件/循环 | 活按什么顺序干 |
| 调度执行 | 就绪队列 + 优先级 + 并发上限 + 能力匹配 | 谁先干、同时干几个 |
| 结果验证 | 硬验证（沙箱跑）+ 软验证（裁判打分） | 干得对不对 |
| 反馈优化 | 错误卡片回灌 → 重写 → 再验证，最多 3 轮 | 不对就改，改到对 |

## 我们凭什么赢（就三条，别多说）

1. **验收是机器判定的**，不是模型自述。所以我们的成绩可以被第三方复现。
2. **循环有外部观察者**（Loop Watchdog）。所以"自我循环"不等于"无限重试"——错误数不降就升级、重复调用就掐断、超限就带病历交付。
3. **全过程可见可干预**。行业中"用户中途接管 Agent"还是公认的开放问题，我们在这一块给出了能跑的实现。

## 主流程（背下来，画白板上就这个）

```
一句话需求
   ↓ analyst 拆解  → 验收条件 + 假设 + 歧义（有阻塞歧义就停下来问人）
   ↓ builder 生成  → index.html
   ↓ ┌ 硬验证（沙箱，10~30s）── 报错 N 条
     └ 软裁判（LLM）─────────── 打 1~5 分，不阻断
   ↓ 失败？→ 错误归一化成 ≤3 张卡片 → fixer 重写 → 回到硬验证（≤3 轮）
   ↓ 通过 → 打包 → 人工确认 → 交付 + 核验报告
   
   全程：事件流实时推送，随时可中断/插入/续跑
```

## 答辩大概率被问的 6 个问题（照这个答）

**Q1：你们和 Dify / LangChain 有什么区别？**
A：它们是编排框架，我们是**带闭环验收的编排平台**。差别在于我们内置了"跑起来验证 + 失败回灌"这一环，而且调度跳转由状态机决定、不让模型临场决定（这点业界实测过，交给模型会产生长尾）。

**Q2：多 Agent 有必要吗？一个 Agent 多调几次不行吗？**
A：我们的实验里有第三组"并行但无核验"，专门回答这个——多 Agent 本身不值钱，值钱的是**验证角色和执行角色的对抗关系**。

**Q3：LLM 裁判会不会被幻觉骗？**
A：会，所以**它不负责判定"能不能跑"**。能不能跑是沙箱判的，是二值事实。LLM 只被允许评价它没法被机械验证的部分（好不好玩），而且它的结论不阻断交付。

**Q4：怎么保证循环一定停？**
A：四道闸——轮次上限 3、调用指纹去重、错误数连续两轮不降就升级、超限带缺陷交付。而且判这些的是外部观察者，不是循环自己。

**Q5：你这个算什么创新？**
A：不在算法复杂度上，在**闭环的设计**上：把"产物可机器验收"这个前提用足了，所以验证是硬的；再用事件流把过程和产物绑定，所以可复现、可中断、可回放。

**Q6：exe 能生成吗？**
A：架构里留了可插拔的打包器接口，当前实现是单文件 HTML。exe 是下个 stage——我们不把 11 天的工期赌在打包调试上，但路是通的。

## 三个数字（跑完实验填进来，只记这三个）

- **一次可运行率**：首轮 95%（19/20）→ 最终 100%（20/20）
- **收敛轮次**：中位数 0 轮（最大 1，上限 3 轮）
- **报错下降**：第 1 轮平均 0.1 条 → 修复后 0 条

> 只会这三组数字，也比背一堆功能有用。评委问性能，就答这三个 + p95 耗时。

## 心智防跑偏（每次想加功能时看这一条）

> **分镜里没有镜头的功能，不做。**
> 3~5 分钟视频只能讲：一句话需求 → 拆解 → 生成 → 跑挂了 → 回灌修 → 跑通了 → 中途插入一句 → 收敛曲线。
> 讲不到的地方，就是不该花时间的地方。
